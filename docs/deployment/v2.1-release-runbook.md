# Graha Motor POS V2.1 Release Runbook

Deployments are started manually with **Deploy Graha Motor** using
`workflow_dispatch` from `main`. The required target selector defaults to
`staging`; select `production` deliberately to request a production deployment.
Both paths run the same tests, safety checks, and artifact creation first.
Production never deploys on push or merge and requires approval through the
GitHub `production` Environment. Staging remains optional and independent.

   Configure `staging` similarly if staging approval is desired.

   rejects dispatches from any ref other than `main`, but repository branch
   restrictions are an external control and must be configured by an admin.

## Before each release

1. Before dispatching, compare production's read-only migration status with
   `production-migrations.json`. Review every listed migration, checksum, order,
   lock and compatibility impact. Use `[]` only when no production migration is
   pending. Never populate the manifest from live database output automatically.
   The V2.1 entry was selected from the candidate's committed migration delta;
   this is not proof of the production pending list. Review the `users` enum
   definition, data compatibility, table size and lock impact before authorizing
   that release. Nonempty manifests require MariaDB session limits: 15 seconds
   for locks and 120 seconds per statement. MariaDB attempts to interrupt timed
   out statements, but this is not a guarantee of atomic rollback or a wall-clock
   limit for the whole migration. Rehearse the DDL and recovery before activation.
2. Confirm the production checkout is clean and its configured schema is
   correct. Confirm PHP CLI 8.2+, `pdo_mysql`, zlib, Git, Composer, `flock`, `curl`,
   and archive tooling. Reserve a maintenance window and verify file-based
   maintenance mode. Workers, queued jobs and requests already in flight must
   be drained separately; the HTTP maintenance switch cannot stop them.
   The production database must use a single explicit TCP
   host (not `localhost`), with no socket, URL, custom PDO options, or read/write
   split. Staging requires the separately provisioned schema and account
   `u163968914_gm_staging@127.0.0.1`. Do not enable staging dispatch until its
   routine and proxy grant checks pass as well.
3. Verify `mysqldump` is installed and the application's MySQL account can
   dump the configured database, routines, triggers, and events. The SSH user must be
   able to create a private `/home/<user>/grahamotor-backups` directory. The
   workflow does not use database credentials from GitHub; the backup helper
   reads the application's local Laravel configuration without printing it.
4. Start **Deploy Graha Motor** from `main`, select `production`, review the
   displayed commit and artifact SHA-256, then wait for a separate authorized
   reviewer to approve the production Environment gate.
5. Confirm the HTTP 200 health check, POS login, checkout and existing records.

## Backup and migration gate

For each environment, the remote script writes a gzip-compressed MySQL dump to
`$HOME/grahamotor-backups` with mode-restricted permissions. It requires:

- `mysqldump` exited successfully and emitted a MySQL/MariaDB dump header;
- the compressed dump can be read to completion;
- a SHA-256 sidecar exists and matches the dump;
- the evidence files are regular, non-symlink files under the canonical backup
  directory.

Any missing, malformed, unreadable, or mismatched evidence stops the deploy
before staging or production migrations. The CI job's migration is against its
disposable MySQL service and is not a live database migration. Backups are not
automatically pruned. The dump is evidence of a successful export, not proof of
a restore; the operator must test restore procedures to a separate database
before the first production release and on a regular schedule.

Before replacing production code, the guard compares the entire release
inventory against migration history, verifies each authorized file and checksum,
and requires the exact reviewed pending order. It checks again after the verified
backup and immediately before executing only the authorized paths, using the
verified artifact manifest. The database identity must remain the same before
backup, before migration, and after rebuilding caches. The runner
and host both validate the uploaded archive SHA-256 and embedded landed SHA.
The host checks the artifact's manifest, migration files, helpers and generated
assets against the exact Git commit before using the release.

## Owner provisioning and rollback limits

The workflow never runs seeders, Tinker, or account-creation commands. Initial
Owner/admin provisioning must be performed interactively by an authorized
operator outside CI, using the project's approved secure procedure. Do not run
`DatabaseSeeder` or `AdminSeeder`: the current `AdminSeeder` contains a
hard-coded password and is not a safe provisioning path. Secure Owner
provisioning remains a release prerequisite until that process is confirmed.

The repository also contains legacy `deploy.sh` and `composer deploy` entry
points. CI rejects workflow references to these entry points, but that does not
stop an operator or external controller from using them on the server. Do not
activate until the operator confirms those paths are excluded from normal
deployment and no other process can run migrations during the release window.

The workflow only advances a server checkout to a commit that is a descendant
of its current commit. It does not automate code rollback or database restore.
Laravel migrations may be irreversible or may have changed live data; a failed
release must be assessed migration-by-migration. Prefer a reviewed forward-fix.
Restoring a database backup requires a separate, explicitly authorized recovery
plan, maintenance window, and data-loss assessment. Do not use this workflow
to roll a server back to an older commit.

## Failure handling

- Failed tests or build: no deployment job runs.
- Production runs serialize in Actions and under a server lock. A newer pending
  run can replace an older pending run. A stale or already-deployed SHA is
  refused; reconcile the latest main head without bypassing the release gates.
- A private in-progress marker is written before live application mutation.
  Failure or interruption leaves it in place, blocking the next release. The
  application enters maintenance before checkout. It leaves maintenance only
  after migration and cache steps succeed. If the subsequent public health
  check fails, the script attempts to return to maintenance. The
  operator must reconcile code, schema and live health under the same server lock
  and obtain recovery authorization before clearing it. Never auto-roll back.
- Failed backup evidence: migrations do not start.
- Failed SSH transfer: the always-run cleanup step attempts to remove only the
  validated `grahamotor-build-<run_id>` directory. If the SSH host is
  unreachable, inspect the exact path manually before any cleanup; never
  remove its parent or a sibling directory.
- Failed health check after deployment: inspect server/application logs and
  use the recovery limits above; no automatic rollback is attempted.
