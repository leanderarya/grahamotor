# Graha Motor POS V2.1 Release Runbook

This workflow deploys one tested commit from `main` to staging, verifies the
staging health endpoint, then waits for production environment approval before
deploying the same commit. It does not deploy on a push. The deployment script
rejects dirty server checkouts, non-forward releases, unverified database
backups, and cleanup targets outside the approved run-specific directory or
`public/build`.

## GitHub configuration

Configure these settings before merging the workflow:

1. Create GitHub environments named `staging` and `production`.
2. Require approval from named release reviewers in both environments. Prevent
   self-review and administrator bypass where the repository plan/settings
   permit it. The production reviewers must be different from the deploy
   initiator.
3. Protect `main`: require pull requests and the relevant CI checks, and limit
   who can update it. Keep this deployment workflow's trigger as
   `workflow_dispatch` only.
4. Confirm no Hostinger hPanel Git deployment, webhook, cron pull, or other
   workflow also writes to either application path. This repository change
   cannot inspect account-side deployment controllers.
5. Add staging environment secrets:
   - `STAGING_HOSTINGER_SSH_HOST`
   - `STAGING_HOSTINGER_SSH_USER`
   - `STAGING_HOSTINGER_SSH_PORT`
   - `STAGING_HOSTINGER_SSH_PRIVATE_KEY`
   - `STAGING_HOSTINGER_SSH_FINGERPRINT`
6. Add staging environment variables:
   - `STAGING_APP_PATH`: canonical absolute path to a separate staging Git
     checkout with its own `.env` and non-production database.
   - `STAGING_HEALTHCHECK_URL`: HTTPS health endpoint with no credentials in
     the URL.
7. Add production environment secrets:
   - `HOSTINGER_SSH_HOST`
   - `HOSTINGER_SSH_USER`
   - `HOSTINGER_SSH_PORT`
   - `HOSTINGER_SSH_PRIVATE_KEY`
   - `HOSTINGER_SSH_FINGERPRINT`
8. Add the production environment variable `PRODUCTION_HEALTHCHECK_URL`.
   Store SSH keys as environment secrets, never in repository files, variables,
   workflow output, or chat.
   Obtain each SSH host fingerprint through a trusted Hostinger/account-owner
   channel and verify it before saving. Do not trust an unverified first
   connection or disable fingerprint checking.
9. Provision both server checkouts with the approved Git remote and an existing
   `.env`. Keep staging and production databases separate. The production path
   is fixed at
   `/home/u163968914/domains/cahayaarkana.site/public_html/grahamotor`; the
   temporary upload parent is fixed at `/home/u163968914`.
10. Use distinct staging and production hosts, application paths, databases,
    private keys, and host fingerprints. Do not expose production credentials
    to the staging environment.

`environment:` in YAML binds a job to an environment but cannot create its
review rules. Repository administrators must configure reviewers and bypass
policy in GitHub settings. Until then, the workflow is not protected for
production use.

## Before each release

1. Merge the intended release to `main`; do not dispatch from another ref.
2. Review pending migrations and confirm the deployed staging database is
   isolated. Ensure the current staging and production checkouts are clean and
   have not advanced beyond the selected commit.
   Before approval, an authorized operator should inspect production migration
   status read-only with `php artisan migrate:status`; stop if it differs from
   the expected staging/release state.
3. Verify `mysqldump` is installed and the application's MySQL account can
   dump the configured database, routines, and triggers. The SSH user must be
   able to create a private `/home/<user>/grahamotor-backups` directory. The
   workflow does not use database credentials from GitHub; the backup helper
   reads the application's local Laravel configuration without printing it.
4. Start **Deploy Graha Motor** manually on `main`. Approve staging, inspect
   application behavior and migration status, and confirm its health check
   before approving production.
5. Review the commit SHA and artifact SHA-256 shown in the run, then review the
   production diff and migration impact at the production approval gate.
   Approve only the same run that passed staging.
6. Confirm the production HTTP health check, POS login, checkout, and existing
   records after deployment.

## Backup and migration gate

For each environment, the remote script writes a gzip-compressed MySQL dump to
`$HOME/grahamotor-backups` with mode-restricted permissions. Before running
`php artisan migrate --force`, it requires all of the following:

- `mysqldump` exited successfully and emitted a MySQL/MariaDB dump header;
- the compressed dump can be read to completion;
- a SHA-256 sidecar exists and matches the dump;
- the evidence files are regular, non-symlink files under the canonical backup
  directory.

Any missing, malformed, unreadable, or mismatched evidence stops the deploy
before staging or production migrations. The CI job's migration is against its
disposable MySQL service and is not a live database migration. Backups are not
automatically pruned. The dump is evidence of a successful export, not proof of
a restore; the operator must test restore procedures to a separate database
before the first production release and on a regular schedule.

## Owner provisioning and rollback limits

The workflow never runs seeders, Tinker, or account-creation commands. Initial
Owner/admin provisioning must be performed interactively by an authorized
operator outside CI, using the project's approved secure procedure. Do not run
`DatabaseSeeder` or `AdminSeeder`: the current `AdminSeeder` contains a
hard-coded password and is not a safe provisioning path. Secure Owner
provisioning remains a release prerequisite until that process is confirmed.

The repository also contains legacy `deploy.sh` and `composer deploy` entry
points that are not called by this workflow and do not use this backup gate.
Do not use them for staging or production releases. Their retirement or
hardening is a separate operator decision; until then they remain an
ungated manual bypass if an operator invokes them.

The workflow only advances a server checkout to a commit that is a descendant
of its current commit. It does not automate code rollback or database restore.
Laravel migrations may be irreversible or may have changed live data; a failed
release must be assessed migration-by-migration. Prefer a reviewed forward-fix.
Restoring a database backup requires a separate, explicitly authorized recovery
plan, maintenance window, and data-loss assessment. Do not use this workflow
to roll a server back to an older commit.

## Failure handling

- Failed tests or build: no deployment job runs.
- Failed staging approval, backup, migration, or health check: production is
  blocked by the staging dependency.
- Failed production approval: production deployment does not start.
- Failed backup evidence: migrations do not start.
- Failed SSH transfer: the always-run cleanup step attempts to remove only the
  validated `grahamotor-build-<run_id>` directory. If the SSH host is
  unreachable, inspect the exact path manually before any cleanup; never
  remove its parent or a sibling directory.
- Failed health check after deployment: inspect server/application logs and
  use the recovery limits above; no automatic rollback is attempted.
