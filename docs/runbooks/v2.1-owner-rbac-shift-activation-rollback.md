# V2.1 Owner, RBAC, and Shift Activation / Rollback

This runbook is procedural only. It was not executed against staging or production.
Use it only within an independently authorized maintenance or release window.

## Activation

1. Confirm the target release, database, and maintenance window. Take and verify a
   restorable database backup using the environment's approved backup procedure.
2. Check the current migration state:

   ```sh
   php artisan migrate:status
   ```

   Confirm `2026_11_17_000001_add_owner_role_and_shift_override_audits` is pending
   and that no unexpected migrations will be applied.
3. Apply migrations using the normal release procedure:

   ```sh
   php artisan migrate --force
   ```

4. Provision the first Owner from an interactive terminal. Do not pass the
   password as a command-line argument or place it in shell history:

   ```sh
   php artisan owner:create --name="Owner Name" --email="owner@example.com"
   ```

   Enter the password at the hidden prompt. The command requires at least 12
   characters, asks for confirmation, creates an audit record, and refuses
   non-interactive execution.
5. Verify the migration status, Owner sign-in, and access to Owner-only financial
   reports. Confirm existing Admin accounts remain Admin and active. Do not
   promote an existing Admin to Owner as part of activation.
6. Review the cashier roster. Admins may manage cashier accounts and view omzet;
   only Owners may activate an account or access HPP, margin, and profit reports.
7. For overdue shifts, Admin/Owner overrides must include a reason. Confirm the
   audit entry is visible before considering the shift resolved. Payments and
   drafts remain bound to their original cashier session.

## Rollback

1. Stop the release procedure and assess the failure before changing data. Do not
   delete Owner accounts, user-management audit rows, or shift-override audit
   rows to make rollback possible.
2. Check `php artisan migrate:status`. The migration can be rolled back only when
   it is the latest applied migration selected for rollback, both audit tables
   are empty, and no Owner account exists. `--step=1` rolls back the latest
   applied migration, so verify that it is this migration. If a later migration
   has been applied, do not use this command; get a separately reviewed rollback
   plan. The migration guard intentionally refuses to discard audit history or
   remove the Owner role while accounts remain.
3. If all preconditions are verified and the approved release owner chooses
   rollback, take and verify another restorable backup, then roll back one
   migration:

   ```sh
   php artisan migrate:rollback --step=1 --force
   ```

   Recheck migration status and application health using the approved release
   checks.
4. If any audit entry or Owner account exists, do not remove that data and do
   not force the schema rollback. Keep the migration in place and use a
   forward-fix or a separately reviewed compatibility plan.

## Shift incident handling

- The shift cutoff is midnight in `Asia/Jakarta`.
- A cashier cannot pay after cutoff. Admin/Owner must close the overdue session
  with a reason; the closure is audited.
- Do not manually rewrite a draft's `cashier_session_id`, replay a payment under
  a new session, or delete the old draft. Investigate pending/offline payments
  against the original session and transaction history first.

## Content Security Policy

- Non-admin pages use a per-response nonce for first-party inline scripts,
  Ziggy routes, Vite tags, and inline style elements. The only nonce-free
  inline style exceptions are SHA-256 hashes for the fixed NProgress and PIN
  `shake` style blocks. Production CSP does not allow `unsafe-eval`,
  `unsafe-inline` scripts, or a hard-coded LAN origin.
- The local Vite HMR allowlist is restricted to loopback port `5173` and is
  enabled only in the `local` environment. Do not expose the Vite server on a
  LAN address to satisfy CSP.
- Filament v3 remains a documented exception: its Livewire/Alpine runtime uses
  `new Function`, and its panel layout emits inline scripts and style elements.
  Therefore `unsafe-eval` and `unsafe-inline` scripts are limited to `/admin`;
  inline style elements are also allowed only there. Style attributes remain
  allowed for React/Filament UI behavior. Remove these exceptions only after
  replacing those runtime requirements and verifying the full admin panel.
- The QR scanner script is pinned to `html5-qrcode` 2.3.8 and protected by
  Subresource Integrity. CSP allows only that exact CDN asset on admin pages.
